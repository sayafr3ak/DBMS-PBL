1. Introduction

1.1 Problem identification

Police stations record complaints (FIRs), investigation diaries, seized evidence, court dates and custody hand-overs in separate paper registers. Such unstructured registers make it hard to answer basic questions — Which cases are pending and with whom? Where is exhibit X right now? Who held it on a given date? — and, most importantly, they weaken the chain of custody: a missing or overlapping hand-over entry can make evidence inadmissible in court.

1.2 Scope

PCETS is a relational database and web application for one police district (several stations). It covers complaint registration, officer assignment, the investigation diary, evidence registration and custody transfers, witnesses, accused persons, charges, court references, case status workflow with a full audit trail, search and reporting. Court case management beyond references/hearing dates, payroll and FIR filing with external systems (CCTNS) are out of scope.

1.3 Objectives

  • Design a normalized (3NF) relational schema for complaints, persons, officers, assignments, activities, evidence, custody logs, witnesses, charges, court references and status histories.
  • Enforce the business rules inside the database — unique complaint/evidence IDs, complete custody transfer, valid case status, no overlapping custody and mandatory closure details — using keys, CHECK constraints and triggers.
  • Provide views and reports: pending cases, officer load, evidence location, custody history, witnesses, case timeline and closures.
  • Build a secure, validated, transaction-aware application with role-based access for station staff.
  • Demonstrate correctness through systematic automated testing.

3.2 Non-functional requirements

  • Integrity: every business rule is enforced by MySQL so it holds even if the application is bypassed.
  • Atomicity: multi-step operations (registration, custody transfer, closure, lead replacement) run as single transactions.
  • Security: role-based access for the acting user, CSRF tokens, parameterised SQL only.
  • Auditability: custody log is append-only, status history cannot be edited or deleted, complaints cannot be deleted.
  • Performance: indexes on all frequently searched/joined columns; views pre-join common report data.
  • Usability: responsive UI (desktop and mobile), light/dark theme, field-level error messages, printable case file and custody sheet.

6.2 Normal forms

  • 1NF — every attribute is atomic: there are no repeating groups (multiple accused, witnesses, charges, custody steps and status changes are stored as rows in their own tables, never as lists in a column).
  • 2NF — the only composite primary key is COMPLAINT_ACCUSED(complaint_id, person_id); its non-key attributes (accused_status, added_at, remarks) describe the pair, not either part alone, so there is no partial dependency. All other tables have single-column keys.
  • 3NF — in every relation each determinant of a non-trivial FD is a (candidate) key, so there are no transitive dependencies (the schema is in fact in BCNF).

8. Integrity constraints and business rules

8.1 Mandatory business rules

RuleHow it is enforced
R1 Unique complaint / evidence IDsUNIQUE uq_complaint_no, uq_evidence_no; numbers generated by triggers trg_complaint_bi / trg_evidence_bi in format CMP-YYYY-NNNNN / EVD-YYYY-NNNNN; CHECK with REGEXP on the format; numbers cannot be changed (trg_complaint_bu)
R2 Complete custody transferNOT NULL on to_officer, location, purpose, received_at; CHECK chk_custody_from (every non-seizure entry names the handing officer); trigger trg_custody_bi: handing officer must be the current holder, previous period must be released, new period must start exactly when the previous ended (no gap); remarks mandatory in the app for broken seal / return / disposal
R3 Valid case statusCHECK chk_complaint_status (5 values); trigger trg_complaint_bu enforces the workflow (REGISTERED→UNDER_INVESTIGATION→CHARGE_SHEETED→IN_COURT→CLOSED, closure from any open state, re-open from CLOSED) and preconditions (officer assigned, ≥1 charge, court reference)
R4 No overlapping custodyUNIQUE (evidence_id, open_key) on a generated column — at most one open custody period per item; interval-overlap check in trg_custody_bi; append-only log (trg_custody_bu, trg_custody_bd); final RETURN/DISPOSAL ends the chain
R5 Closure details requiredCHECK chk_complaint_closure: status CLOSED ⇔ closure_date, closure_type, closure_remarks and closed_by are all present; CHECK chk_complaint_closuredate: closure not before registration

8.2 Additional rules

  • Only one active LEAD officer per case and no duplicate active assignment (UNIQUE on generated columns lead_key, active_key).
  • Inactive officers cannot be assigned or receive custody; activities only by officers assigned at that time; nothing can be added to a closed case.
  • An accused cannot be a witness (or complainant) in the same case; charges only against accused of that case (composite FK).
  • Court reference only after charge-sheet; verdict only when the court case is DISPOSED (CHECK).
  • ID-proof formats per type (Aadhaar, PAN, Voter ID, Passport, DL), Indian mobile numbers and badge numbers validated by CHECK + REGEXP.
  • Complaints cannot be deleted and the status history cannot be modified (triggers).

-- Q22 Time spent in each status (LEAD window function over the audit trail)
WITH status_periods AS (
    SELECT complaint_id, new_status, changed_at,
           LEAD(changed_at) OVER (PARTITION BY complaint_id ORDER BY changed_at) AS next_change
      FROM status_history)
SELECT c.complaint_no, sp.new_status, sp.changed_at,
       DATEDIFF(COALESCE(sp.next_change, NOW()), sp.changed_at) AS days_in_status
  FROM status_periods sp JOIN complaint c ON c.complaint_id = sp.complaint_id;

-- Q17 Open cases with no activity in the last 30 days (NOT EXISTS)
SELECT c.complaint_no, c.title, c.status FROM complaint c
 WHERE c.status <> 'CLOSED'
   AND NOT EXISTS (SELECT 1 FROM investigation_activity a
                    WHERE a.complaint_id = c.complaint_id
                      AND a.activity_time >= CURDATE() - INTERVAL 30 DAY);

12. Transactions and concurrency

The application uses an explicit START TRANSACTION … COMMIT block (db.transaction(), isolation READ COMMITTED); any exception triggers ROLLBACK, so a multi-step operation is all-or-nothing:

OperationStatements in one transaction
Register complaintINSERT person (if new) → INSERT complaint (+ trigger history) → optional INSERT assignment + UPDATE status
Register evidenceINSERT evidence_item → INSERT custody (INITIAL_SEIZURE) → optional release + INSERT custody (STORAGE)
Custody transferSELECT … FOR UPDATE on the open custody row → UPDATE released_at → INSERT new period
Status changeSELECT status FOR UPDATE (optimistic check) → UPDATE complaint (+ audit trigger) → relieve officers on closure
Replace lead / role changeLock current lead → relieve → INSERT new assignment
Add witness / accused with new personINSERT person → INSERT witness / complaint_accused

The row lock taken with FOR UPDATE serialises two custodians trying to transfer the same exhibit at the same moment — the second waits, then fails the no-overlap check instead of creating two current holders. Test TC-10 proves rollback: a valid new person is not saved when the complaint insert fails. Stored procedures sp_transfer_custody and sp_close_complaint show the same pattern in pure SQL with an EXIT HANDLER that rolls back.

13.3 Validation and error handling

  • Two layers: application validation (required fields, lengths, formats, dates not in the future, allowed choices) gives field-level messages; the database re-checks everything as the final authority.
  • MySQL errors are translated into readable messages: 1062 duplicate → which key, 3819 CHECK → rule description, 1451/1452 FK, 1644 trigger SIGNAL text, 1048 NOT NULL. The form is re-displayed with the user's input and the dialog re-opened.
  • Custom 400/403/404/500/503 pages; unexpected errors are logged to logs/app.log; a database-down page explains how to fix the connection.

13.4 Security

  • No login page (not required by the brief): the acting user is chosen from the sidebar; session cookies are HttpOnly + SameSite. app_user keeps PBKDF2 password hashes so a login screen can be re-enabled for real deployment.
  • Role-based access checked on every route; CSRF token on every POST form; all SQL parameterised (no string concatenation of user input).
  • ID-proof numbers masked in lists; protected-witness names hidden in the printable case file.

16. Conclusion and future scope

PCETS replaces fragmented station registers with a single normalized database whose rules cannot be bypassed: complaint and evidence identifiers are unique, every custody hand-over is complete and gap-free, custody periods never overlap, case status follows a valid workflow with a permanent audit trail, and a case cannot be closed without its closure details. The Flask application exposes all required operations — complaint registration, officer assignment, activity logging, evidence registration, custody transfer, witness entry, status update and reporting — with validation, transactions, role-based security and a modern responsive interface. {{ results.ran }} automated tests and {{ integrity|length }} database-level scenarios verify the behaviour.

Future scope

  • Attachments (photos, PDFs of statements) stored with hash values to prove evidence files are unaltered.
  • QR codes on evidence tags scanned at hand-over; SMS/e-mail alerts for hearing dates and long lab stays.
  • Integration with CCTNS and e-Courts APIs; multi-district partitioning; read replicas for analytics.

Appendix A. Installation and running

1. Install MySQL 8.0 and Python 3.10+
2. pip install -r requirements.txt
3. Edit config.ini  (MySQL host / user / password)
4. python setup_db.py          # creates police_evidence_db, loads schema, triggers, views and sample data
5. python run.py               # open http://127.0.0.1:5000
6. python -m unittest -v tests.test_app     # automated tests (uses a separate test database)

No login: the app opens as admin; switch to vikram (SHO), anjali (IO), suresh (Custodian)… with "Acting as" in the sidebar
SQL only:     run sql/00 … sql/04 in MySQL Workbench; sql/05 = report queries; sql/06 = negative tests (mysql --force)
