Abstract

Police stations still record complaints, investigation diaries, seized evidence and custody hand-overs in separate paper registers. Such registers make it difficult to know which cases are pending, who is working on them and — most critically — where each piece of evidence is and who has held it. A missing or overlapping custody entry can make evidence inadmissible in court.

This project designs and implements PCETS, a relational database and web application for police complaint and evidence tracking. The conceptual ER model covers complaints, persons, officers, assignments, investigation activities, evidence items, custody logs, witnesses, charges, court references and status histories. It was converted into 14 relations normalized to 3NF and implemented in MySQL 8.0 with primary, foreign, unique, NOT NULL, CHECK and DEFAULT constraints, 17 triggers, stored procedures, 9 views and secondary indexes. The five mandatory business rules — unique complaint/evidence IDs, complete custody transfer, valid case status, no overlapping custody and mandatory closure details — are enforced by the database itself. A Python (Flask) application provides complaint registration, officer assignment, activity logging, evidence registration, custody transfer, witness entry, status updates and twelve reports. 43 automated tests and 26 live integrity scenarios verify the system, and the application has been deployed to the cloud.

1. Introduction

1.1 Problem identification

In a typical station, the complaint register, case diary, malkhana (evidence) register and court diary are maintained separately and by hand. This causes duplicated data (the same person written in many registers), inconsistent updates, no quick way to search or report, and weak chain-of-custody traceability: nothing stops two officers from both being recorded as holding an exhibit, or a hand-over being written without the receiving officer.

1.2 Objectives

  • Identify the entities, attributes, relationships and user roles of a police complaint and evidence system.
  • Build an ER model and convert it into a relational schema normalized up to Third Normal Form.
  • Enforce the business rules with keys, CHECK constraints and triggers so they hold even if the application is bypassed.
  • Write SQL for joins, sub-queries, aggregation and views for pending cases, officer load, evidence location, custody history, witnesses, case timeline and closures.
  • Develop a validated, transaction-aware Python front end and test it systematically.

1.3 Scope

The system covers one district with several police stations: complaint registration, assignment of officers, the investigation diary, evidence registration and custody, witnesses, accused persons and charges, court references with hearing dates, the case status workflow with a full audit trail, search and reporting. Integration with national systems (CCTNS, e-Courts), payroll and document storage are outside the scope.

  • Performance — indexes on frequently searched columns; views pre-join report data.
  • Usability — responsive interface for desktop and mobile, clear field-level error messages, printable case file.

6.2 Normal forms

  • First Normal Form: every attribute is atomic. Multiple accused, witnesses, charges, custody steps and status changes are stored as rows of their own tables, never as lists inside a column.
  • Second Normal Form: the only composite primary key is COMPLAINT_ACCUSED(complaint_id, person_id). Its non-key attributes describe the pair, not either part alone, so there are no partial dependencies. All other tables have single-column keys.
  • Third Normal Form: in every relation the determinant of each non-trivial FD is a candidate key, so there are no transitive dependencies. The schema is in fact in BCNF.

7. Integrity Constraints and Business Rules

Business ruleHow MySQL enforces it
Unique complaint / evidence IDsUNIQUE keys on complaint_no and evidence_no; numbers generated by triggers in the format CMP-YYYY-NNNNN / EVD-YYYY-NNNNN; CHECK with REGEXP on the format; numbers cannot be changed
Complete custody transferNOT NULL receiving officer, location, purpose and time; CHECK that every non-seizure entry names the handing officer; trigger: handing officer must be the current holder and the new period must start exactly when the previous one ended (no gap)
Valid case statusCHECK limits status to 5 values; trigger enforces the workflow REGISTERED → UNDER_INVESTIGATION → CHARGE_SHEETED → IN_COURT → CLOSED (and re-open) with preconditions: officer assigned, at least one charge, a court reference
No overlapping custodyUNIQUE index on a generated column allows only one open custody period per exhibit; trigger rejects any overlapping time interval; custody log is append-only and cannot be deleted
Closure details requiredCHECK: status CLOSED ⇔ closure date, type, remarks and closing officer all present; closure date cannot precede registration

7.1 Additional constraints

  • One active LEAD officer per case and no duplicate active assignment (UNIQUE indexes on generated columns).
  • Inactive officers cannot be assigned or receive custody; activities only by officers assigned at that time.
  • The accused cannot be a witness or complainant in the same case; charges only against accused of that case.
  • Court reference only after charge-sheet; a verdict only when the court case is disposed.
  • Formats of Aadhaar, PAN, Voter ID, passport, driving licence, mobile and badge numbers checked with CHECK + REGEXP.

9. SQL Queries and Reports

The file 05_report_queries.sql contains 25 queries demonstrating INNER and LEFT joins, GROUP BY / HAVING / ROLLUP, conditional aggregation, nested and correlated sub-queries, EXISTS / NOT EXISTS, derived tables, CTEs and window functions. Examples:

-- Officers handling more active cases than average (nested sub-query)
SELECT full_name, active_cases FROM v_officer_load
 WHERE active_cases > (SELECT AVG(active_cases) FROM v_officer_load WHERE is_active = 1);

-- Cases per station by status with closure rate (aggregation)
SELECT s.station_name, COUNT(*) AS total,
       SUM(c.status = 'CLOSED') AS closed,
       ROUND(100 * SUM(c.status = 'CLOSED') / COUNT(*), 1) AS closure_rate_pct
  FROM complaint c JOIN station s ON s.station_id = c.station_id
 GROUP BY s.station_name;

-- Open cases with no activity in the last 30 days (NOT EXISTS)
SELECT c.complaint_no, c.title FROM complaint c
 WHERE c.status <> 'CLOSED'
   AND NOT EXISTS (SELECT 1 FROM investigation_activity a
                    WHERE a.complaint_id = c.complaint_id
                      AND a.activity_time >= CURDATE() - INTERVAL 30 DAY);

-- Chain-of-custody integrity audit (window function LAG)
WITH chain AS (
  SELECT evidence_id, received_at, from_officer_id,
         LAG(released_at)   OVER (PARTITION BY evidence_id ORDER BY received_at) AS prev_released,
         LAG(to_officer_id) OVER (PARTITION BY evidence_id ORDER BY received_at) AS prev_holder
    FROM custody_log)
SELECT COUNT(*) AS broken_links FROM chain
 WHERE NOT ((prev_released IS NULL AND from_officer_id IS NULL)
         OR (prev_released = received_at AND prev_holder = from_officer_id));

The application offers twelve reports built on these views: pending cases, officer workload, evidence location, custody history, witness register, case timeline, closures, station summary, category analysis, upcoming hearings, stale cases and the custody integrity audit. Each report can be filtered, printed and exported to CSV.

10.3 Validation and error handling

  • Two layers of validation: the application checks required fields, lengths, formats, allowed values and that dates are not in the future, then MySQL re-checks everything.
  • Database errors are translated into readable messages — duplicate key, CHECK violation, foreign key, trigger message — and the form is shown again with the user's input.
  • Friendly 403, 404 and 500 pages; unexpected errors are logged to a file.

10.4 Sample data

The database is populated with realistic data for four Pune police stations: 16 officers, 40 persons, 20 complaints at every stage of the workflow (robbery, burglary, cyber fraud, narcotics, missing person, domestic violence …), 22 evidence items with 56 custody periods, 56 investigation activities, 11 witnesses, 10 charges, 3 court references and 52 status-history rows. All rows were inserted through the triggers, which shows that the business rules are mutually consistent.

13. Deployment

The application is deployed to the cloud with a managed MySQL database on Clever Cloud; the web app runs under gunicorn (Clever Cloud and Render). The free MySQL plan does not allow triggers (binary logging without SUPER privilege) and allows only five connections, so the application has a hosted mode: when no triggers exist it issues the CMP/EVD numbers, writes the status history and checks the trigger rules itself, and it opens one database connection per request. Keys, CHECK constraints and foreign keys are still enforced by MySQL. On a local MySQL installation the full trigger set is active.

14. Conclusion and Future Scope

PCETS replaces separate station registers with one normalized database whose rules cannot be bypassed. Complaint and evidence numbers are unique, every custody hand-over is complete and gap-free, custody periods never overlap, case status follows a valid workflow with a permanent audit trail, and a case cannot be closed without its closure details. The Python application provides every required function — complaint registration, officer assignment, activity logging, evidence registration, custody transfer, witness entry, status update and reporting — with validation, transactions and role-based access. The project gave practical experience in ER modelling, normalization, constraint design, triggers, views, transactions, indexing and systematic testing.

Future scope

  • Upload photos and documents with each exhibit and store a hash to prove the file is unaltered.
  • QR codes on evidence tags scanned at every hand-over.
  • SMS / e-mail reminders for hearing dates and exhibits staying too long in the forensic lab.
  • Integration with CCTNS and e-Courts; a proper login screen with two-factor authentication for real deployment.
